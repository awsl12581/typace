# 0001. 采用共享世界状态的分层多卫星动力学与控制架构

## Context

Mission 要求把 typace 扩展为多卫星、地球/月球 patched-conic 仿真。所有卫星必须共享同一仿真时钟；未被玩家接管的卫星继续自主运行，玩家归还控制权后自主系统还要从当前真实状态重新规划。平动、姿态、推进剂、电力和生命周期会共同影响轨道传播、控制和事件检测，渲染与 Textual 面板只能展示这些状态。终端和 SDL 后端还必须运行同一套 Textual 应用，并保持确定性的更新顺序。

因此架构需要同时守住三条边界：目录输入先完成严格校验和历元归一化；物理传播统一处理中心引力、地球 J2、阻力、有限推力和姿态；制导、控制、自主飞行、交会检测和渲染只能通过明确的运行状态或世界快照协作。Mission 目前只有设计和实现要求，尚无代码或测试证据证明该选择已经落地。

## Decision

采用单一世界时钟和共享的可变卫星运行状态，按“目录与模型 -> 物理传播与事件 -> 制导/控制/自主 -> 世界快照 -> 渲染与 Textual 界面 -> 终端或 SDL 后端”分层实现。地球和月球之间使用 patched-conic 切换主天体；每个主天体相对状态统一由中心引力、适用时的地球 J2 和阻力、有限推力以及质量流失共同传播。自动驾驶和玩家控制都把命令作用于这份状态。后端只切换输入与输出适配，不复制物理或业务逻辑。

## Rejected

- **为自动驾驶、手动驾驶和画面展示维护平行轨道状态:** 三份状态在接管、归还控制权或销毁事件时容易漂移，无法保证自主系统从玩家当前状态继续规划。
- **让渲染器或 Textual 界面直接驱动物理:** 会把动力学、控制和生命周期耦合到显示帧率及后端差异，难以保持统一时钟、后台运行和终端/SDL 一致性。
- **用单一大型仿真模块同时承担目录、物理、规划和界面:** 能减少初期文件数量，却会模糊依赖方向，使模型验证、替换积分器和独立测试变得困难。
- **改用 N 体或天文历表级传播:** 精度更高，但会引入当前玩法和验证目标不需要的模型、数据与计算成本；本次任务只要求地月 patched-conic 及列明的摄动力。

## Consequences

共享状态消除了控制模式切换时的同步问题，并让 64 颗卫星的后台更新、事件记录和双后端验证使用同一条确定性路径。分层边界也允许目录校验、动力学、控制和渲染分别测试，且快照可以作为界面只读契约。

代价是运行状态的生命周期、命令时序和快照一致性必须明确设计；任何绕过世界更新顺序的直接修改都会破坏确定性。有限推力、姿态、电力和多卫星事件使实现复杂度高于简单的二体轨道演示，且该 ADR 在代码与真实 SDL/OpenGL 测试落地前保持 `draft`。

## Amendment - 2026-09-17

批准规格细化了模块和依赖所有权：自动驾驶拆为导航、目标、规划、制导、姿态控制、执行和安全监督，编排器不包含领域算法；Astropy 唯一负责时间、单位及其覆盖的标准参考系，`lamberthub.izzo2015` 唯一负责零圈 Lambert 求解，SciPy 唯一负责通用求根与最小化。对应自制算法、fallback、兼容层和运行时算法切换不进入生产路径。程序完全离线，卫星数据只从本地 JSON 加载；所有对外文本统一净化绝对路径和个人敏感信息。
